# Architecture phase 5: Change scope, use cases, delegation

Objective: a run builds one typed `ChangeSet` (all repos of a change), derives a `ChangeScope` (direct and indirect reach ending at routes and operations), turns it into deterministic `UseCaseCandidate[]`, admits a lead plan only when every direct candidate is covered or dropped with a reason, briefs each sidekick with its candidates, and grades plan and delivery coverage per candidate. Source: `docs/architecture-remediation.md` (plan phase 5; closes C1–C7, N1, N3, N8). Baseline: HEAD `209dca5f` (2026-10-25).
Branch: `fix/failure-observation-conflict` (owner rule: one branch, no PR split). Delivery: work-unit commits (about 400 authored lines each, advisory); a task whose Risk names a high-risk item ships as its own commit. Runner: `node --import ./test-setup.mjs --import tsx --test <file>` under Node v24.11.0. Phase gate: the use-case-coverage grader reports plan and delivery coverage per candidate (S10).

- **S1b (P5.1b): coalescing queued runs of one app; companion entries through the run.** Pushes that land while a run of the same app is still queued join that run instead of queuing another; the run reads every entry's diff, gates on every entry's deploy and checks every entry out at its head.
  - Closes: C1. Depends on: S1a.
  - Why: a feature landing in front and back becomes two serialized runs, each blind to the other's diff (`webhook-routing.ts:30-37`, `runner.ts:336` creates one record and one job per request). `JobQueue` (`src/server/queue.ts`) is an opaque promise chain, so a queued job cannot be found or edited today.
  - Change:
    - New `src/server/pending-change-sets.ts` (shell, beside the queue): a registry keyed by run id of the change sets of runs that are queued and not started. All calls are synchronous, so the queue's single-threaded ordering is the lock.
    - Eligibility to merge (all must hold): source `webhook`; mode `diff`; target `e2e`; no `parentRunId`, `purpose` or `guidance`; same app, same `shadow`; the queued run has not been taken; no entry would exceed the app's declared repos (`appConfig.repo` plus `appConfig.services`). A code-target app never coalesces (its runs are per repo).
    - Merge rule per repo: a repo not yet in the set adds an entry; a repo already in it extends its range (`baseSha` = the earlier entry's base, `headSha` = the later head; when the earlier entry has no base, the range starts at the later entry's base if it has one, else the head alone). A push that does not descend from the held head is still merged (range semantics are git's: `base..head`); the base of the union is the earlier base.
    - `enqueueTrackedRun` (`runner.ts:336`) calls `offer` first: on a merge it returns the existing run id, logs `[qa] coalesced <repo>@<sha> into <runId>`, creates no record and no job, and publishes a run event so the TUI shows the extra entry. `runPipeline` reads its set from `take(runId)`.
